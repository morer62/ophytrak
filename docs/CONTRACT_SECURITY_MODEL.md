# Contract Security Model

## Security Boundary

Contract signing is a public-link workflow protected by an HMAC token. The signed artifact is a generated PDF plus an audit row.

The current security boundary is:

- token required;
- token expiry required;
- HMAC validated with `VNV_SECRET_KEY`;
- signer user id included in token;
- order or suborder id included in token;
- signed PDF hash stored;
- IP and user agent stored;
- duplicate signing blocked by existing signed document records.

## Answers From Audit

1. Contract content comes from `orders_contracts`.
2. Signing happens in public `order-access` routes.
3. Signature is captured as uploaded image or typed initials.
4. Main contract upload is recorded as method; receipt acceptance can store the signature image path.
5. PDF is generated by `ContractPdfGenerator` or `OrderAcceptancePdfGenerator`.
6. PDF URL is stored in `document_logs.file_path` or `orders_acceptance_contracts.file_path`.
7. Viewing currently depends on routes and storage URL; protected downloads are recommended.
8. Public links use HMAC token and expiry.
9. Token is not persisted yet.
10. Token expires through `exp`.
11. Token reuse is now blocked after signing by existing document records.
12. IP, user agent and generated timestamp are stored.
13. Main contract PDF hash is stored in `document_logs.hash`.
14. Main signature hash is not stored separately yet.
15. Receipt acceptance stores PDF hash in `orders_acceptance_contracts.hash`.
16. Existing PDFs are not overwritten by the signing flow.
17. Admin/private visibility still needs protected download review.
18. Firmante is tied to token `user_id`; stronger email/signed_by fields are recommended.
19. Tables: `orders_contracts`, `document_logs`, `orders_acceptance_contracts`, `orders_acceptance_contract_template`.
20. Existing order access and payment flows depend on this logic.
21. Main risks: stateless token, public storage URL, no signature hash field, no persisted token state.
22. Team members can reuse the PDF generator/audit pattern.
23. Recommended before full duplication: persisted token/status table and protected downloads.

## Team Member Contract Model

Team member contracts use `team_member_contracts` for assignment, signing, upload and validation status.

Employee/team member contract templates are separate from order contracts. They live in `team_member_contract_templates` and are created from the employee contract admin screen, not from `orders_contracts`.

Validated statuses:

```text
SIGNED
VALIDATED
MANUALLY_UPLOADED
```

Blocking behavior:

- `TeamMemberContractService::isClockInAllowed()` checks this table when it exists.
- Since the table is applied, clock-in is blocked until a valid contract row exists.
- Pending, rejected or expired contracts do not allow clock-in.

## Required Admin Capabilities

Admin/owner should be able to:

- assign a contract template to a team member;
- create employee-only contract templates;
- generate/send a signing link;
- upload a manually signed PDF;
- mark contract as validated or rejected;
- see status in team member lists;
- view/download signed PDF through protected routes.

## Required Team Member Capabilities

Team member should be able to:

- see pending contract;
- sign electronically;
- see validated/signed PDF;
- download only their own contract;
- see a clear blocked clock-in message when contract is missing.

## QA Checklist

Client contract:

- Open valid token.
- Submit invalid token: rejected.
- Submit expired token: rejected.
- Sign once: PDF and audit row created.
- Re-submit same token after signing: blocked.
- Confirm `document_logs.hash` stores the PDF hash.
- Confirm IP/user agent are stored.

Team member contract:

- Assign contract from `panel/planner-hub/management/users/contracts?id=TEAM_MEMBER_ID`.
- Attempt clock-in: blocked.
- Sign as Level 4 from `panel/planner-hub/team/contracts`.
- Confirm PDF path/hash are stored.
- Confirm clock-in becomes allowed when status is `SIGNED`.
- Upload manual signed PDF from admin route.
- Confirm status becomes `MANUALLY_UPLOADED`.
- Attempt clock-in: allowed.
- Confirm direct POST cannot bypass the block.
- Confirm admin upload records file path/hash/user/timestamp.
